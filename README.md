# ai-cam

Privacy-first local AI camera stack (Windows host + Docker Desktop WSL2).

## Repo Map (What Each File Does)
- `docker-compose.yml`: defines the containers, ports, volumes, and the private network.
- `.env.example`: safe template of configuration values (copy to `.env`).
- `.env`: runtime secrets and settings (gitignored).
- `frigate/config.template.yml`: Frigate config template without secrets.
- `data/config/frigate.yml`: rendered Frigate config WITH RTSP URLs (gitignored, generated).
- `mosquitto/mosquitto.conf`: MQTT broker config.
- `mediamtx/mediamtx.yml`: optional RTSP proxy config (generated by script).
- `scripts/`: helper scripts (render config, privacy mode, manual clip, etc).
- `data/`: persistent runtime data (clips, recordings, models, logs).

## Mini Glossary (Plain English)
- MQTT: local “message bus” for events/commands between services (Mosquitto is the server).
- RTSP: camera video stream protocol used on your LAN.
- NVR: software that records camera feeds and produces events/clips (Frigate).
- STT: Speech-to-Text (Whisper).
- TTS: Text-to-Speech (Piper).
- Wake word: keyword that starts listening (“hey jarvis”), handled by OpenWakeWord.
- WebRTC: low-latency live video delivery to a browser (used by Frigate live view).

## Goals (MVP)
- RTSP ingest from Reolink E1 (PTZ)
- Event-based recording (no 24/7 retention)
- Clips saved under `./data/clips/`
- Retention rules in Frigate config
- Live view UI (Frigate + Home Assistant)
- Local-only, no cloud streaming, no port forwarding
- Mobile access only via VPN (Tailscale on Windows host)

## Setup
1. Create `.env` from `.env.example` and fill camera credentials.
   For privacy-first defaults in Frigate, keep:
   - `FRIGATE_SNAPSHOTS_ENABLED=0` (no still images)
   - `FRIGATE_RECORD_AUDIO_PRESET=preset-record-generic-audio-aac` (recordings include audio when stream provides it)
2. Verify camera RTSP works (VLC):

```text
rtsp://CAMERA_USER:CAMERA_PASS@CAMERA_HOST:554/h264Preview_01_main
```

3. Render Frigate config (keeps secrets out of git):
```bash
./scripts/render_frigate_config.sh
```

## Better Voice (TTS)
Piper is the simplest fully-local TTS, but it can sound robotic.

If you want a more human voice locally, use `Chatterbox` first (local + OpenAI-compatible TTS API).

1. Render Chatterbox config:
```bash
./scripts/render_chatterbox_config.sh
```

2. Start Chatterbox service:
```bash
docker compose --profile tts-chatterbox up -d --build chatterbox-tts
```

3. Probe service:
```bash
./scripts/chatterbox_probe.sh
```

4. Install Home Assistant custom TTS provider:
```bash
./scripts/install_ha_chatterbox_tts.sh
```

5. Add/replace `tts:` in `data/homeassistant/configuration.yaml`:
```yaml
tts:
  - platform: aihub_chatterbox
    name: Chatterbox Lokal
    url: http://chatterbox-tts:8000/tts
    model: chatterbox
    # Use clone mode with your own Swedish reference voice.
    # Place the file at: data/chatterbox/reference_audio/sv_ref.wav
    voice: clone:sv_ref.wav
    response_format: wav
    language: sv
    timeout: 120
```

6. Restart Home Assistant:
```bash
docker compose restart homeassistant
```

7. In Home Assistant Assist pipeline, pick `Chatterbox Lokal` as TTS engine.

Fallback (if Chatterbox GPU build fails): keep `haxtts` profile and `marytts` block.

Privacy note:
- This is still local-only; we do not publish the TTS port to your LAN.
- If you ever choose a cloud TTS later, it typically sends only text (not raw audio/video), but it still leaks the spoken content.

### Troubleshooting: CUDA Error 500 "named symbol not found" (WSL2 + Docker)
If `haxtts` (or any PyTorch CUDA container) keeps restarting with an error like:
- `cudaGetDeviceCount() ... Error 500: named symbol not found`

Then your Docker Desktop / WSL2 GPU plumbing is out of date for your NVIDIA Windows driver.
This is a known WSL2 container issue that is often fixed by updating Docker Desktop to a newer version.

Fix:
1. Update Docker Desktop on Windows to the latest stable release.
2. Restart Windows (or at least restart Docker Desktop + WSL).
3. Recreate the container:
```bash
COMPOSE_COMPATIBILITY=1 docker compose --profile tts-xtts up -d --force-recreate haxtts
docker compose --profile tts-xtts logs --tail 200 haxtts
```

## Tailscale-Only Access (Recommended)
If you want UIs reachable only over Tailscale (not your LAN), set `UI_BIND_ADDR` in `.env` to your Windows host's
Tailscale IPv4 (usually `100.x.y.z`) instead of `0.0.0.0`.

Example:
```text
UI_BIND_ADDR=100.123.45.67
```

## Firewall Lockdown (Windows host)
Restrict inbound access to the UI ports to Tailscale only:
- Ports: `8123` (Home Assistant), `5000` (Frigate), `8555` (Frigate WebRTC)
- Allow from: your Tailscale subnet (`100.64.0.0/10`) or your specific Tailnet device IPs
- Block everything else

Example (PowerShell as Administrator), allow only Tailscale subnet:
```powershell
$ports = "8123","5000","8555"
foreach ($p in $ports) {
  New-NetFirewallRule -DisplayName "ai-cam allow tailscale $p" -Direction Inbound -Action Allow -Protocol TCP -LocalPort $p -RemoteAddress 100.64.0.0/10
}
New-NetFirewallRule -DisplayName "ai-cam allow tailscale 8555 udp" -Direction Inbound -Action Allow -Protocol UDP -LocalPort 8555 -RemoteAddress 100.64.0.0/10
```


```bash
docker run --rm --network ai-cam-net curlimages/curl:8.6.0 -fsS http://aihub:8080/v1/integrations/ha/status
```

Check Codex routing config seen by aihub:
```bash
docker run --rm --network ai-cam-net curlimages/curl:8.6.0 -fsS http://aihub:8080/v1/integrations/codex/status
```

If you want aihub to execute HA actions (notify/spotify), set:
- `AIHUB_HA_TOKEN` (long-lived token from Home Assistant profile)
- `AIHUB_HA_NOTIFY_SERVICE` (e.g. `notify.mobile_app_<device>` or `persistent_notification.create`)
- Optional dance action:
  - `AIHUB_HA_SPOTIFY_ENTITY_ID`
  - `AIHUB_DANCE_SPOTIFY_URI`

If you want aihub replies to play on camera speaker, set:
- `AIHUB_CAMERA_SPEAK_ENABLED=1`
- `AIHUB_CAMERA_SPEAK_URL=http://camera-voice-bridge:8091/v1/speak`
- `CAMERA_VOICE_DEFAULT_STREAM=reolink_e1pro_main` (default stream key in this repo)

AIHub memory/workout storage is local SQLite:
- `AIHUB_DB_PATH=/data/aihub.db` (container path, persisted in `./data/aihub`)

Vision loop now supports live RTSP ingest (not only single snapshots):
- `AIHUB_VISION_VIDEO_ENABLED=1`
- `AIHUB_VISION_VIDEO_RTSP_URL=rtsp://frigate:8554/reolink_e1pro_main`
- `AIHUB_VISION_ANALYZER_MODE=auto` (`auto|cv|vlm`)
- `AIHUB_VISION_CV_ENABLED=1` enables local OpenCV rep counter for workout tasks.

Quick verification after restart:
```bash
docker run --rm --network ai-cam-net curlimages/curl:8.6.0 -fsS http://aihub:8080/v1/health
```
Look for:
- `vision_video.has_frame=true` (live frames arriving)
- `vision_rep_counter.available=true` (local CV rep analyzer active)

Audio privacy gate (recommended ON):
- `AIHUB_AUDIO_REQUIRE_WAKE_OR_ACTIVE=1`
- Behavior: audio text is ignored unless it includes wake phrase (e.g. `hej codex`) or belongs to an active conversation TTL window.

Camera mic listener privacy:
- `camera-listener` only forwards text to AIHub after wake phrase.
- Raw camera audio is processed locally and not persisted by listener.

## Local LLM (ChatGPT-Like)
To get a more "chatbot" feel, run a local LLM and use it as the Assist conversation agent.

### Option A (Recommended): Ollama On Windows Host (GPU, Fast)
This gives the biggest latency improvement on RTX 4070 right now.

1. Install Ollama on Windows and start it.
2. Pull a model on Windows:
```text
ollama pull llama3.1:8b
```
3. Make Ollama reachable from Docker (Windows):
   - Quit Ollama (tray icon) so it restarts with new settings.
   - Set a Windows user environment variable:
     - `OLLAMA_HOST=0.0.0.0:11434` (simple, but must be firewalled), or
     - `OLLAMA_HOST=<your Windows Tailscale IP>:11434` (Tailnet-only exposure).
   - Start Ollama again (Start menu).
   - Optional sanity check on Windows:
     - `netstat -ano | findstr :11434` should show it listening on the address you chose.
4. From WSL, verify Docker can reach Windows-Ollama:
```bash
# If you used OLLAMA_HOST=0.0.0.0:11434
./scripts/ollama_probe.sh http://host.docker.internal:11434

# If you used OLLAMA_HOST=<your Windows Tailscale IP>:11434
./scripts/ollama_probe.sh http://<your Windows Tailscale IP>:11434
```
5. In Home Assistant:
   - `Inställningar` -> `Enheter och tjänster` -> `Lägg till integration` -> `Ollama`
   - URL: `http://host.docker.internal:11434` (0.0.0.0 bind) or `http://<your Windows Tailscale IP>:11434` (Tailscale bind)
   - Model: `llama3.1:8b`

Then set your Assist assistant's `Konversationsagent` to the Ollama agent.

Note: if you enable "Tänk efter innan svar" and get an error like `"llama3.1:8b" does not support thinking`,
turn that option off for this model.

### Option B: Ollama In Docker (Usually CPU, Slower Here)
Enable the Docker Ollama service explicitly:
```bash
docker compose --profile docker-ollama up -d ollama
./scripts/ollama_pull.sh llama3.1:8b
```

In Home Assistant, URL becomes:
- `http://ollama:11434`

Performance note (WSL2 + Docker Desktop):
- We verified GPU works in containers in general, but `ollama/ollama` may still run CPU-only in this setup.
- If latency is too high, use Option A.
